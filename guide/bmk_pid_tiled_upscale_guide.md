# BMK PiD Tiled Upscale — 핵심 가이드 (v2)

NVIDIA PiD(PixelDiT) 4배 업스케일을 타일 루프로 수행하여, 입력 해상도 제한 없이
4K 이상 이미지도 처리하는 노드입니다.

---

## 품질을 지배하는 단 하나의 변수: 패스당 캔버스 면적

1280×960 소스로 동일 조건 3시드 실측한 결과입니다.

| 패스당 캔버스 | 학습(4096²=16.8MP) 대비 | 결과 |
|---|---|---|
| 2048×5120 = 10.5MP | 63% | 부드럽고 형태 응집력 있음 |
| 4096×4096 = 16.8MP | 100% | 무난, 약간 무름 |
| 5120×5120 = 26.2MP | **156%** | **형태 경계가 톱니처럼 거칠어짐** |

PiD 가 한 번의 forward pass 에서 그리는 픽셀 수가 학습 규모를 넘으면 경계 응집력이
무너집니다. 이 노드는 두 장치로 그 면적을 통제합니다.

1. **자동 타일링** — 소스 종횡비를 유지한 채, 타일 면적이 `pid_input_size²` 근처가
   되도록 격자를 자동 계산.
2. **타일 내부 컨텍스트 윈도우** — 타일 출력을 높이 축으로 잘라 여러 패스로 분할.
   패스당 캔버스가 더 줄고, 겹침 구간은 매 스텝 예측의 앙상블이 되어 비간섭성
   그레인이 상쇄됩니다.

**1타일 + 컨텍스트 윈도우 = 코어 ContextWindows 방식(AIO)과 동일한 동작**입니다.

## 자동 타일링이 실제로 내놓는 결과

기본값(`pid_input_size 1024`, `context_pixel 128`, `core_overlap 64`,
`tile_tolerance 1.3`, 창 on / 2048 / 512):

| 입력 | 격자 | PiD 입력 | 창 | 패스 캔버스 | 패딩 낭비 | 출력 |
|---|---|---|---|---|---|---|
| 1280×960 | 1×1 | 1280×960 | 3 | **10.5MP** | 0% | 5120×3840 |
| 1024×1024 | 1×1 | 1024×1024 | 3 | 8.4MP | 0% | 4096×4096 |
| 1248×1824 | 2×1 | 912×2080 | 6 | 7.5MP | 37% | 4992×7296 |
| 2048×2048 | 2×2 | 1312×1312 | 4 | 10.7MP | 27% | 8192×8192 |
| 3840×2160 | 3×3 | 1584×1024 | 3 | 13.0MP | 21% | 15360×8640 |
| 4096×4096 | 4×4 | 1328×1328 | 4 | 10.9MP | 13% | 16384×16384 |
| 8192×8192 | 8×7 | 1344×1488 | 4 | 11.0MP | 8% | 32768×32768 |

- 1280×960 이 **패딩 0 으로 1타일**이 되고 패스 캔버스가 AIO 와 정확히 같은 10.5MP
  입니다. 이게 v2 의 핵심 목표였습니다.
- **타일이 1개면 `context_pixel` 은 자동으로 0 이 됩니다.** 컨텍스트 링이 전부 미러
  패딩이라 실제 컨텍스트가 아니고 연산만 +52% 늘리기 때문입니다(로그에 표시).
- 격자 선택은 `타일 수 × (1 + 종횡비 편차)` 최소화이고, 편차 0.5(≈1.65배)를 넘는
  조합은 배제합니다. 이게 없으면 창이 높이를 처리해주는 만큼 최적화가 "얇고 긴 띠"로
  붕괴합니다(4096² → 320×4096 스트립 13장).

## 타일 기하

```
core_w × core_h : 결과에 반영되는 영역 (자동 결정, 소스 종횡비 유지)
PiD 입력         = (core_w + 2×context_pixel) × (core_h + 2×context_pixel)
stride          = core − core_overlap

┌──────────────── PiD 입력 ────────────────┐
│ ctx │            core            │ ctx │
└─────┴────────────────────────────┴─────┘
         ↑ 생성에만 쓰고 페이스트에서 제외 ↑
```

경계는 가상 캔버스로 처리합니다(BMK Flexible Tile SEGS 의 virtual_canvas 와 같은
사고방식). 좌상단 기준 고정 스트라이드로 코어를 깔고, 이미지 밖은 `padding_fill` 로
채우며, 마지막 타일을 가장자리에 스냅하지 않아 타일 크기가 끝까지 균일합니다.
출력에서 패딩분은 ×4 비례로 잘라냅니다.

feather 는 `core_overlap` 구간에만 걸리며, 인접 타일 가중치 합이 밴드 전 구간에서
정확히 1.0 이 되도록 검증되어 있습니다(밝기 단차 없음).

## 과채도 억제 4층

| 층 | 수단 | 위치 |
|---|---|---|
| 1 | `degrade_sigma` 0.06 | 이 노드 (기본값) |
| 2 | 코어 페이스트 — 각 픽셀은 단 한 타일에서만 옴 | 이 노드 (내재) |
| 3 | per-tile color match | 이 노드 (`color_match`) |
| 4 | 전역 저주파 톤 이식 | **BMK Wavelet Tone Restore** (별도 연결) |

3층은 출력을 소스 해상도로 area 다운샘플한 뒤 통계를 비교합니다. PiD 가 새로 만든
고주파가 std 에 섞여 눌리는 것을 막기 위한 주파수 공정 비교입니다. `mean` 은 채널
평균만 맞춰 색 편이를 잡고 대비는 건드리지 않으며, `mean_std` 는 채도 폭주까지
억제합니다(게인은 [0.5, 2.0] 으로 제한). **타일이 1개면 효과가 거의 없습니다.**

## 배선

```
BMK PiD Loader ──(pid_ctx)──┐    ← encode_vae 를 위젯에 지정하면
KSampler ──(LATENT)─────────┤       Load VAE 배선이 필요 없음
   또는                     ├─→ BMK PiD Tiled Upscale ─→ IMAGE (×4)
Load Image ──(IMAGE)────────┘                              │
                                                           ↓
              원본 ──(reference)──→ BMK Wavelet Tone Restore
                                                           ↓
                                            ImageScaleBy (lanczos, 0.5)
```

- `latent` 와 `image` 중 하나만 연결. 둘 다면 **latent 우선**.
- `latent` 경로가 VAE 왕복이 없어 더 정확·빠릅니다. 단 `color_match` 를 쓰려면
  소스 타일 디코드용 인코딩 VAE 가 필요합니다(로더 위젯 또는 포트).
- 이 노드는 출력을 clamp 하지 않습니다. 하이라이트 헤드룸을 Wavelet Tone Restore
  까지 넘기기 위함이며, 코어 VAEDecode 와 같은 거동입니다.
- `downscale_by` 는 없습니다. 외부 `ImageScaleBy` 를 쓰세요 — 축소 배율만 바꿀 때
  재샘플링을 피할 수 있습니다.

### VAE 두 개를 혼동하지 마세요

| 용도 | 값 | 지정 위치 |
|---|---|---|
| PiD 디코드 | `pixel_space` **고정** | 로더의 `pid_vae` |
| 입력 인코딩 | 생성 백본과 같은 계열 (`qwen_image_vae` 등) | 로더의 `encode_vae` **또는** 업스케일 노드의 `vae_encode` 포트 |

인코딩 VAE 는 **포트 > 로더 위젯** 순으로 해석됩니다. PiD 모델과 인코딩 VAE 는
latent 계열로 묶여 있어(qwenimage PiD ↔ qwen VAE) 대개 한 번 정하면 바뀌지 않으므로,
로더 위젯에 지정해 두면 Load VAE 노드와 배선을 통째로 없앨 수 있습니다.
`latent` 직결 + `color_match=off` 로만 쓴다면 `none` 으로 두어 불필요한 로드를
피하세요.

`latent_format` 은 **생성 모델이 아니라 인코딩에 쓴 VAE** 를 따릅니다. Flux VAE
(`ae.safetensors`)로 인코딩해 놓고 `qwenimage` 를 고르면 채널 수가 둘 다 16 이라
에러 없이 통과한 뒤 결과만 무너집니다. 실행 시 로그의
`src 1280x960 (qwenimage, 16ch/8x)` 를 확인하세요.

## 파라미터

| 파라미터 | 기본 | 설명 |
|---|---|---|
| `pid_input_size` | 1024 | 타일 크기의 **면적 기준값**(변 길이 아님). 체크포인트 학습 크기와 일치 |
| `tile_tolerance` | 1.3 | 기준 면적의 몇 배까지 쪼개지 않을지. 창 on 이면 코어 면적, off 면 PiD 입력 면적 기준 |
| `context_pixel` | 128 | 코어 밖 컨텍스트. 1타일이면 자동 0 |
| `core_overlap` | 64 | 코어 겹침 = feather 밴드 폭. 1타일이면 무의미 |
| `padding_fill` | reflect | 패딩이 이미지보다 크면 replicate 자동 폴백 |
| `context_windows` | on | 타일 내부 창 분할. **끄면 타일이 잘게 쪼개집니다**(면적 예산 기준이 바뀜) |
| `context_length` | 2048 | 창 높이(출력 px). 타일 출력 높이가 이하면 건너뜀 |
| `context_overlap` | 512 | 창 겹침(출력 px). 클수록 앙상블 구간↑, 느려짐 |
| `fuse_method` | pyramid | pyramid / overlap-linear(저사양·빠름) |
| `degrade_sigma` | 0.06 | 낮을수록 원본 충실 = 색 편이 억제. 0.05~0.10 |
| `latent_format` | qwenimage | flux2(Klein)만 16× 배율. 채널 수 교차 검증됨 |
| `seed_mode` | same | same 권장 |
| `color_match` | mean | mean / mean_std / off |
| `model_shift` | 0.0 | 과한 샤픈/헤일로 완화. 아래 실측 참고 |
| `tile_shape` | auto | auto / square(v1 재현, 비교 테스트 전용) |

로더 위젯: `pid_model` / `clip_name` / `pid_vae`(pixel_space 고정) / `prompt` /
`weight_dtype` / `encode_vae`(none 기본)
| `accum_dtype` | fp32 | 초대형 입력에서 RAM 이 빠듯하면 fp16 |

## `model_shift` — 샤픈 완화 트레이드오프 (4096² 실측)

```
             HF평균    HF p99.9   백클립%   흑클립%
shift 0.0   0.01844    0.2689     0.92     0.32
shift 3.0   0.01658    0.2445     0.50     0.11
shift 8.0   0.01632    0.2091     0.72     0.12
```

- **0 → 3**: 평균 디테일 −10%, 대신 백클립 −46% · 흑클립 −66%. 트레이드오프가 명확.
- **3 → 8**: 평균 디테일은 **−1.4% 뿐**인데(사실상 유지) 극단 오버슈트(p99.9)만
  **−14% 추가**로 깎임. 헤일로 억제 대비 비용이 가장 좋은 구간.
- 백클립 최소점은 3 부근(8 에서 0.50 → 0.72 로 소폭 반등).

권장 탐색 구간은 **2~8**입니다. 선이 튀고 경계에 흰 테가 보이면 올리고, 디테일이
아쉬우면 내리세요. 기본값 0.0 은 AIO 와 동일한 무보정 상태입니다.

## `tile_shape` — v1 방식 재현

`square` 로 두면 v1 처럼 정사각 타일을 강제합니다. 이때 `pid_input_size` 의 의미가
바뀝니다 — 면적 기준값이 아니라 **PiD 입력 한 변**이고, `core = pid_input_size −
2×context_pixel` 입니다. `tile_tolerance`·종횡비 제약·면적/패스 상한이 전부 무시되고,
단일 타일 시 `context_pixel` 자동 하향도 적용되지 않습니다.

v1 재현 설정: `tile_shape=square`, `pid_input_size=1024`, `context_pixel=0`,
`core_overlap=0`, `context_windows=off`, `color_match=off`

| 입력 | square (v1 재현) | auto (기본값) |
|---|---|---|
| 1024×1024 | 1×1, PiD 1024² , 낭비 0% | 1×1, PiD 1024², 낭비 0% |
| 2048×2048 | 2×2, PiD 1024², 낭비 0% | 2×2, PiD 1312², 낭비 27% |
| 4096×4096 | 4×4, PiD 1024², 낭비 0% | 4×4, PiD 1328², 낭비 13% |
| 1280×960 | 2×1, PiD 1024², **낭비 71%** | 1×1, PiD 1280×960, 낭비 0% |
| 3840×2160 | 4×3, PiD 1024², **낭비 52%** | 3×3, PiD 1584×1024, 낭비 21% |

정사각 소스는 두 모드가 사실상 같지만, 비정사각 소스에서 square 는 미러 패딩으로
50~85% 를 낭비합니다. **비교 테스트 목적이 아니면 auto 를 쓰세요.**

square 에 `context_windows=on` 을 조합할 수도 있습니다(패스 캔버스 16.8 → 8.4MP).
v1 에는 없던 조합이라 순수 재현은 아니지만, "정사각 타일 + 창 앙상블" 을 따로
평가하고 싶을 때 유용합니다.

## 평가할 때 주의 — 시드 변동이 방식 변동만큼 큽니다

실측 결과입니다(1280×960, 5120×3840 출력, 평균 절대차):

```
같은 방식 다른 시드 : 9.95 ~ 9.99 / 255
다른 방식          : 10.23 ~ 10.38 / 255
```

**방식을 바꾼 차이가 시드를 바꾼 차이보다 3~4% 클 뿐입니다.** `model_shift` 차이도
같은 척도로 4.06~6.54/255 로, 시드 변동보다 작습니다.

한 장씩 눈으로 비교하면 계속 시드 운에 속습니다. 최소 3시드 세트로 보고, 가능하면
고주파 에너지·클리핑 비율처럼 **방향성 있는 지표**를 함께 확인하세요. 클리핑 같은
지표는 시드 노이즈에 묻히지 않고 일관되게 나타납니다.

## 튜닝 순서

1. 기본값으로 실행 → 콘솔 로그에서 격자·PiD 입력·창 수·패스 캔버스 확인.
2. **패스 캔버스가 16.8MP 를 넘으면** `context_length` 를 낮추거나
   `tile_tolerance` 를 내립니다.
3. 이음새가 보이면 → `core_overlap` 64 → 128.
4. 경계에 색 단차 → `color_match` 를 `mean` → `mean_std`.
5. 디테일 부족 → `degrade_sigma` 0.06 → 0.10 (4번과 함께 조정).
6. 전역 톤이 밍숭맹숭 → BMK Wavelet Tone Restore 의 `levels` 조정.

## 트러블슈팅

- **타일이 예상보다 잘게 쪼개짐** — `context_windows` 가 꺼져 있는지 확인하세요.
  창이 꺼지면 면적 예산이 PiD 입력 기준(코어+컨텍스트)으로 바뀌어 훨씬 빡빡해집니다.
- **타일 하나조차 OOM** — `context_windows` 를 켜거나 `pid_input_size` 를 낮추세요.
  노드가 1회 자동 재시도합니다.
- **결과 색이 완전히 다름** — `latent_format` 과 인코딩 VAE 불일치. 콘솔 로그 확인.
- **`pid_vae` 에러** — `pixel_space` 이외를 고르면 로더가 즉시 막습니다.
- **짧은 면이 작은 이미지** — 1타일로 동작은 하지만 PiD 가 1024급을 기대하므로
  디테일이 부족할 수 있습니다. 앞단에서 미리 확대해 넣으세요.
- **배치 입력** — 항목마다 전체 캔버스를 만들어 마지막에 이어 붙입니다.
  초대형 입력에서는 batch 1 로.

## 설치

1. `bmk_pid_tiled_upscale.py` 를 `ComfyUI_BMK_Nodes/` 에 배치.
2. `__init__.py` 의 `_NODE_MODULES` 에 `"bmk_pid_tiled_upscale",` 추가
   (`bmk_load_image_crop` 과 `bmk_run_batch_grid` 사이, 알파벳 순).
3. ComfyUI 재시작 → `BMK/Image` 카테고리에서 두 노드 확인.

v2.1 → v2.2 도 로더에 `encode_vae` 가 맨 뒤에 추가된 것뿐이라 기존 배선이 유지됩니다.

**v1 → v2 는 위젯 구성이 바뀌었습니다.** 기존 워크플로우의 노드는 지우고 다시
추가하세요. v2 → v2.1 은 `tile_shape` 가 위젯 목록 맨 뒤에 추가되었을 뿐이라
기존 v2 배선은 그대로 유지됩니다(값은 기본 auto).

## 한계

- PiD 는 네이티브 4배 고정이라 배율을 고를 수 없습니다. 순 2배가 목표여도 4배 연산
  비용을 지불하고 사후 축소해야 합니다.
- 타일 간 전역 일관성(화면을 가로지르는 넓은 그라데이션)은 타일 방식의 구조적
