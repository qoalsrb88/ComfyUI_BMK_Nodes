# BMK PiD Tiled Upscale — 핵심 가이드 (v2.3)

NVIDIA PiD(PixelDiT) 4배 업스케일을 타일 루프로 수행하여, 입력 해상도 제한 없이
4K 이상 이미지도 처리하는 노드입니다.

> 이 문서는 **설계 근거와 실측 데이터**를 담은 상세본입니다. 처음 쓰신다면
> [빠른 시작](bmk_pid_tiled_upscale_quickstart.md)부터 보세요 — 배선과 권장값만
> 추려 놓았습니다.

---

## 지배 변수는 둘이고, 서로 다른 것을 망가뜨립니다

### 1. 축 길이 → 색 (하드 상한)

**타일 출력의 어느 한 축이라도 학습 변 길이(4096px)를 넘으면 하이라이트가 마젠타로
밀리는 색 회전이 생깁니다.** 1920×1080 소스, 패스 면적을 고정한 채 폭만 바꾼 실측
(보라색 편이 ×1000, 값이 클수록 나쁨):

| 타일 출력 폭 | 패스 캔버스 | 보라색 편이 |
|---|---|---|
| 4096 | 8.4MP (50%) | **6.8** |
| 6144 | 8.7MP (52%) | **24.2** |
| 8192 | 8.4MP (50%) | **31.6** |

반대로 폭을 4096 에 고정하고 패스 면적만 4배(4.2 → 16.8MP)로 늘리면 7.7 / 7.1 /
7.2 / 9.0 으로, 시드 변동폭(±1.1) 안에서 움직이지 않습니다.

- **컨텍스트 윈도우로는 막을 수 없습니다.** 창은 높이만 자르고 폭은 건드리지 않습니다.
- **`model_shift` 로도 막을 수 없습니다.** 8 까지 올려도 33% 밖에 깎이지 않고,
  그 대가로 백클립이 3.4배가 됩니다.
- **`color_match` 와도 무관합니다.** 세 모드 모두 차이가 없습니다.
- 손상은 **크로마에만** 생기고 루마 디테일은 멀쩡합니다. 후단 BMK Wavelet Tone
  Restore 가 약 75% 를 걷어내지만, 입력 오차가 커지면 남는 25% 도 같이 커집니다.

그래서 v2.3 부터 자동 격자는 면적 예산과 **별개로** PiD 입력의 각 축을
`pid_input_size` 이하로 강제합니다. 이건 조절 항목이 아니라 하드 제약입니다.

### 2. 패스당 캔버스 면적 → 형태와 그레인 (소프트 예산)

1280×960 소스, 동일 조건 3시드 실측입니다.

| 패스당 캔버스 | 학습(4096²=16.8MP) 대비 | 결과 |
|---|---|---|
| 2048×5120 = 10.5MP | 63% | 부드럽고 형태 응집력 있음 |
| 4096×4096 = 16.8MP | 100% | 무난, 약간 무름 |
| 5120×5120 = 26.2MP | **156%** | **형태 경계가 톱니처럼 거칠어짐** |

축 상한 안에서 타일을 얼마나 크게 가져갈지를 정하는 예산입니다. 두 장치로 통제합니다.

1. **자동 타일링** — 축 상한을 만족하는 격자 중, 소스 종횡비를 유지하며 타일 면적이
   `pid_input_size²` 근처가 되는 것을 고릅니다.
2. **타일 내부 컨텍스트 윈도우** — 타일 출력을 높이 축으로 잘라 여러 패스로 분할.
   패스당 캔버스가 더 줄고, 겹침 구간은 매 스텝 예측의 앙상블이 되어 비간섭성
   그레인이 상쇄됩니다.

**1타일 + 컨텍스트 윈도우 = 코어 ContextWindows 방식(AIO)과 동일한 동작**입니다.

## 자동 타일링이 실제로 내놓는 결과

기본값(`pid_input_size 1024`, `context_pixel 128`, `core_overlap 64`,
`tile_tolerance 1.3`, 창 on / 2048 / 512):

| 입력 | 격자 | PiD 입력 | 창 | 패스 캔버스 | 패딩 낭비 | 출력 |
|---|---|---|---|---|---|---|
| 1280×960 | 2×2 | 928×768 | 2 | 7.6MP | 12% | 5120×3840 |
| 1024×1024 | 1×1 | 1024×1024 | 3 | 8.4MP | 0% | 4096×4096 |
| 1248×1824 | 2×3 | 912×912 | 3 | 7.5MP | 13% | 4992×7296 |
| 2048×2048 | 3×3 | 992×992 | 3 | 8.1MP | 16% | 8192×8192 |
| 3840×2160 | 6×4 | 960×848 | 2 | 7.9MP | 21% | 15360×8640 |
| 4096×4096 | 6×6 | 992×992 | 3 | 8.1MP | 16% | 16384×16384 |
| 8192×8192 | 12×12 | 1008×1008 | 3 | 8.3MP | 21% | 32768×32768 |

- **PiD 입력이 어느 축도 1024 를 넘지 않습니다.** 축 상한이 걸린 결과이고, 이게
  v2.3 의 핵심입니다. v2.2 까지는 같은 표에서 1280×960 이 1×1(PiD 1280×960),
  3840×2160 이 3×3(PiD 1584×1024)이었는데, 둘 다 축이 학습 크기를 넘어 색 회전이
  나던 조합입니다.
- **대가는 타일 수입니다.** `context_pixel=128` 이면 링이 양쪽에서 예산을 먹어
  코어가 최대 768 로 줄기 때문에 특히 잘게 쪼개집니다. 속도가 아쉬우면
  `context_pixel` 을 0 으로 두세요 — 3840×2160 은 6×4 → 4×3, 8192² 는
  12×12 → 9×9 로 줄어듭니다.
- **컨텍스트 링을 떼면 1타일에 들어가는 경우 `context_pixel` 은 자동으로 0 이
  됩니다.** 1024×1024 가 그 예입니다 — ctx 128 을 붙이면 코어 상한이 768 이라
  2×2 가 되지만, 링은 어차피 전부 미러 패딩이라 실제 컨텍스트가 아니므로 떼는 쪽이
  무조건 낫습니다(로그에 표시). v2.2 까지는 격자가 이미 1×1 일 때만 적용했는데,
  축 상한이 생기면서 판정 기준을 "떼면 1×1 이 되는가"로 넓혔습니다.
- 격자 선택은 `타일 수 × (1 + 종횡비 편차)` 최소화이고, 편차 0.5(≈1.65배)를 넘는
  조합은 배제합니다. 이게 없으면 창이 높이를 처리해주는 만큼 최적화가 "얇고 긴 띠"로
  붕괴합니다(4096² → 320×4096 스트립 13장).

## 타일 기하

```
core_w × core_h : 결과에 반영되는 영역 (자동 결정, 소스 종횡비 유지)
PiD 입력         = (core_w + 2×context_pixel) × (core_h + 2×context_pixel)
stride          = core − core_overlap

┌──────────────── PiD 입력 ────────────────┐
│ ctx │            core            │ ctx │
└─────┴────────────────────────────┴─────┘
         ↑ 생성에만 쓰고 페이스트에서 제외 ↑
```

경계는 가상 캔버스로 처리합니다(BMK Flexible Tile SEGS 의 virtual_canvas 와 같은
사고방식). 좌상단 기준 고정 스트라이드로 코어를 깔고, 이미지 밖은 `padding_fill` 로
채우며, 마지막 타일을 가장자리에 스냅하지 않아 타일 크기가 끝까지 균일합니다.
출력에서 패딩분은 ×4 비례로 잘라냅니다.

feather 는 `core_overlap` 구간에만 걸리며, 인접 타일 가중치 합이 밴드 전 구간에서
정확히 1.0 이 되도록 검증되어 있습니다(밝기 단차 없음).

## 과채도 억제 4층

| 층 | 수단 | 위치 |
|---|---|---|
| 1 | `degrade_sigma` 0.06 | 이 노드 (기본값) |
| 2 | 코어 페이스트 — 각 픽셀은 단 한 타일에서만 옴 | 이 노드 (내재) |
| 3 | per-tile color match | 이 노드 (`color_match`) |
| 4 | 전역 저주파 톤 이식 | **BMK Wavelet Tone Restore** (별도 연결) |

3층은 출력을 소스 해상도로 area 다운샘플한 뒤 통계를 비교합니다. PiD 가 새로 만든
고주파가 std 에 섞여 눌리는 것을 막기 위한 주파수 공정 비교입니다. `mean_std` 는
평균과 표준편차를 모두 맞춰 채도 폭주를 억제합니다(게인은 [0.5, 2.0] 으로 제한).
`mean` 은 평균만 맞추는데, PiD 는 타일 평균을 이미 잘 보존하므로 **실측상 `off` 와
거의 같습니다** — 아래 절 참고. **타일이 1개면 전역 보정이 되어 효과가 줄어듭니다.**

4층이 가장 큰 몫을 합니다. 노드 출력의 크로마 오차 중 약 **75%** 를 Wavelet Tone
Restore 가 걷어냅니다(실측: 노드 출력 30.8 → 최종 6.8). 다만 제거 비율이 일정해서,
입력 오차가 커지면 남는 25% 도 같이 커집니다 — 그래서 애초에 축 상한으로 오차를
만들지 않는 것이 1순위입니다.

## 배선

```
BMK PiD Loader ──(pid_ctx)──┐    ← encode_vae 를 위젯에 지정하면
KSampler ──(LATENT)─────────┤       Load VAE 배선이 필요 없음
   또는                     ├─→ BMK PiD Tiled Upscale ─→ IMAGE (×4)
Load Image ──(IMAGE)────────┘                              │
                                                           ↓
              원본 ──(reference)──→ BMK Wavelet Tone Restore
                                                           ↓
                                            ImageScaleBy (lanczos, 0.5)
```

- `latent` 와 `image` 중 하나만 연결. 둘 다면 **latent 우선**.
- `latent` 경로가 VAE 왕복이 없어 더 정확·빠릅니다. 단 `color_match` 를 쓰려면
  소스 타일 디코드용 인코딩 VAE 가 필요합니다(로더 위젯 또는 포트).
- 이 노드는 출력을 clamp 하지 않습니다. 하이라이트 헤드룸을 Wavelet Tone Restore
  까지 넘기기 위함이며, 코어 VAEDecode 와 같은 거동입니다.
- `downscale_by` 는 없습니다. 외부 `ImageScaleBy` 를 쓰세요 — 축소 배율만 바꿀 때
  재샘플링을 피할 수 있습니다.

### VAE 두 개를 혼동하지 마세요

| 용도 | 값 | 지정 위치 |
|---|---|---|
| PiD 디코드 | `pixel_space` **고정** | 로더의 `pid_vae` |
| 입력 인코딩 | 생성 백본과 같은 계열 (`qwen_image_vae` 등) | 로더의 `encode_vae` **또는** 업스케일 노드의 `vae_encode` 포트 |

인코딩 VAE 는 **포트 > 로더 위젯** 순으로 해석됩니다. PiD 모델과 인코딩 VAE 는
latent 계열로 묶여 있어(qwenimage PiD ↔ qwen VAE) 대개 한 번 정하면 바뀌지 않으므로,
로더 위젯에 지정해 두면 Load VAE 노드와 배선을 통째로 없앨 수 있습니다.
`latent` 직결 + `color_match=off` 로만 쓴다면 `none` 으로 두어 불필요한 로드를
피하세요.

`latent_format` 은 **생성 모델이 아니라 인코딩에 쓴 VAE** 를 따릅니다. Flux VAE
(`ae.safetensors`)로 인코딩해 놓고 `qwenimage` 를 고르면 채널 수가 둘 다 16 이라
에러 없이 통과한 뒤 결과만 무너집니다. 실행 시 로그의
`src 1280x960 (qwenimage, 16ch/8x)` 를 확인하세요.

## 파라미터

| 파라미터 | 기본 | 설명 |
|---|---|---|
| `pid_input_size` | 1024 | **축별 하드 상한 + 면적 기준값.** PiD 입력의 각 축이 이 값을 넘지 못하고, 그 안에서 면적이 이 값의 제곱 근처가 되도록 격자를 정함. 체크포인트 학습 크기와 일치시킬 것 |
| `tile_tolerance` | 1.3 | 기준 **면적**의 몇 배까지 쪼개지 않을지. 축 상한은 이 값과 무관하게 항상 적용. 창 on 이면 코어 면적, off 면 PiD 입력 면적 기준 |
| `context_pixel` | 128 | 코어 밖 컨텍스트. 1타일이면 자동 0 |
| `core_overlap` | 64 | 코어 겹침 = feather 밴드 폭. 1타일이면 무의미 |
| `padding_fill` | reflect | 패딩이 이미지보다 크면 replicate 자동 폴백 |
| `context_windows` | on | 타일 내부 창 분할. **끄면 타일이 잘게 쪼개집니다**(면적 예산 기준이 바뀜) |
| `context_length` | 2048 | 창 높이(출력 px). 타일 출력 높이가 이하면 건너뜀 |
| `context_overlap` | 512 | 창 겹침(출력 px). 클수록 앙상블 구간↑, 느려짐 |
| `fuse_method` | pyramid | pyramid / overlap-linear(저사양·빠름) |
| `degrade_sigma` | 0.06 | 낮을수록 원본 충실 = 색 편이 억제. 0.05~0.10 |
| `latent_format` | qwenimage | flux2(Klein)만 16× 배율. 채널 수 교차 검증됨 |
| `seed_mode` | same | same 권장 |
| `color_match` | **mean_std** | mean_std / mean / off. **`mean` 은 실측상 `off` 와 거의 동일**(아래 참고) |
| `model_shift` | 0.0 | 과한 샤픈/헤일로 완화. 아래 실측 참고 |
| `accum_dtype` | fp32 | 초대형 입력에서 RAM 이 빠듯하면 fp16 |
| `tile_shape` | auto | auto / square(v1 재현, 비교 테스트 전용) |

로더 위젯: `pid_model` / `clip_name` / `pid_vae`(pixel_space 고정) / `prompt` /
`weight_dtype` / `encode_vae`(none 기본)

## `color_match` — `mean` 은 사실상 무동작입니다

1920×1080 소스, 2×2 격자, 3시드 실측입니다.

| 모드 | 백클립% | 흑클립% | 타일 심 불연속 | 루마 고주파 | `off` 대비 평균 절대차 |
|---|---|---|---|---|---|
| `mean_std` | **0.119** | **0.048** | **5.3** (대조군 3.7) | 0.03140 | 2.380 / 255 |
| `mean` | 1.789 | 0.500 | 14.9 | 0.03434 | **0.012 / 255** |
| `off` | 1.784 | 0.498 | 16.9 | 0.03434 | — |

`mean` 과 `off` 의 차이는 평균 절대차 **0.012/255**, 최대 2레벨입니다. 사실상 같은
그림입니다. 이유는 PiD 가 타일 **평균**은 이미 잘 보존하고 **표준편차**만 부풀리기
때문입니다 — 평균만 맞추는 보정은 할 일이 없습니다.

`mean_std` 는 백클립 −93%, 흑클립 −90%, 타일 심 불연속 −65% 를 대가로 루마 고주파를
8.6% 낮춥니다. 이 감소는 손실이 아니라 대비를 소스 통계로 되돌리는 의도된 동작입니다
(고주파 평균과 p99.9 가 같은 비율로 내려갑니다). **그래서 v2.3 부터 기본값입니다.**

색 회전(보라색 번짐)에는 세 모드 모두 효과가 없습니다 — 그건 축 상한의 영역입니다.

## `model_shift` — 노드 출력에는 효과, 최종 출력에는 미미

2소스(1920×1080 / 2768×1186) × 3시드 실측, `0.0 → 3.0` 변화량입니다.

| 지표 | 샘플1 | 샘플2 |
|---|---|---|
| 색 편이 (최종 출력) | −11% | −11.4% |
| 색 편이 (**노드 출력**, 후단 톤 보정 전) | −32% | **−48.6%** |
| 루마 고주파 (디테일) | −0.4% | −0.4% |
| 타일 심 불연속 | 거의 변화 없음 | 비율 1.49 → **1.03** |

**기본값 0.0 을 유지하는 이유**: 최종 출력 기준 이득 −11% 가 시드 변동폭 안입니다.
0.0 은 AIO 와 동일한 무보정 기준선이기도 합니다.

**3.0 이 유리한 경우**: 노드 출력을 그대로 쓰거나(후단 Wavelet Tone Restore 없이),
타일 수가 많은 구성입니다. 디테일 비용이 −0.4% 로 거의 없는데 노드 출력의 색 편이가
1/3~1/2 로 줄고 타일 심이 정리됩니다.

**8.0 은 권하지 않습니다**: 색 편이는 더 줄지만 루마 고주파가 5~6% 빠지고 백클립이
크게 늘어납니다.

> ⚠ v2.2 까지 이 문서에 있던 4096² 클리핑 표(`0→3` 에서 백클립 −46%)는 **두 소스
> 어디에서도 재현되지 않았습니다**(샘플1 +70%, 샘플2 +0.4%). 측정 조건이 기록되지
> 않아 원인을 특정할 수 없어 제거했습니다. 참고로 이 파이프라인은 클리핑을 만드는
> 게 아니라 줄입니다 — 샘플1 원본 백클립 2.44% → 출력 0.12%, 샘플2 원본 27.27% →
> 출력 18.58%.

권장 탐색 구간은 **2~8** 이고, 선이 튀고 경계에 흰 테가 보이면 올리세요.
**색 회전(보라색 번짐)에는 쓰지 마세요** — 8 까지 올려도 33% 밖에 못 깎습니다.

## `tile_shape` — v1 방식 재현

`square` 로 두면 v1 처럼 정사각 타일을 강제합니다. 이때 `pid_input_size` 의 의미가
바뀝니다 — 면적 기준값이 아니라 **PiD 입력 한 변**이고, `core = pid_input_size −
2×context_pixel` 입니다. `tile_tolerance`·종횡비 제약·면적/패스 상한 **그리고 축
상한까지** 전부 무시되고, 단일 타일 시 `context_pixel` 자동 하향도 적용되지 않습니다.

v1 재현 설정: `tile_shape=square`, `pid_input_size=1024`, `context_pixel=0`,
`core_overlap=0`, `context_windows=off`, `color_match=off`

| 입력 | square (v1 재현) | auto (v2.3 기본값) |
|---|---|---|
| 1024×1024 | 1×1, PiD 1024², 낭비 0% | 1×1, PiD 1024², 낭비 0% |
| 2048×2048 | 2×2, PiD 1024², 낭비 0% | 3×3, PiD 992², 낭비 16% |
| 4096×4096 | 4×4, PiD 1024², 낭비 0% | 6×6, PiD 992², 낭비 16% |
| 1280×960 | 2×1, PiD 1024², **낭비 71%** | 2×2, PiD 928×768, 낭비 12% |
| 3840×2160 | 4×3, PiD 1024², **낭비 52%** | 6×4, PiD 960×848, 낭비 21% |

정사각 소스는 두 모드가 사실상 같지만, 비정사각 소스에서 square 는 미러 패딩으로
50~85% 를 낭비합니다. **비교 테스트 목적이 아니면 auto 를 쓰세요.**

다만 축 상한 관점에서는 square 에 구조적 장점이 하나 있습니다. `pid_input_size=1024`
로 두면 타일이 **정확히 학습 크기(PiD 입력 1024² → 출력 4096²)에 고정**되어, 소스가
무엇이든 축 초과가 일어날 수 없습니다. v2.2 까지 "square 가 가장 안정적"이라는 경험칙이
있었다면 이유가 이것입니다 — 정사각형이라 좋은 게 아니라 축 길이가 못 박혀서였습니다.
v2.3 의 auto 는 같은 보장을 낭비 없이 제공합니다.

square 에 `context_windows=on` 을 조합할 수도 있습니다(패스 캔버스 16.8 → 8.4MP).
v1 에는 없던 조합이라 순수 재현은 아니지만, "정사각 타일 + 창 앙상블" 을 따로
평가하고 싶을 때 유용합니다.

## 평가할 때 주의 — 시드 변동이 방식 변동만큼 큽니다

실측 결과입니다(1280×960, 5120×3840 출력, 평균 절대차):

```
같은 방식 다른 시드 : 9.95 ~ 9.99 / 255
다른 방식          : 10.23 ~ 10.38 / 255
```

**방식을 바꾼 차이가 시드를 바꾼 차이보다 3~4% 클 뿐입니다.** `model_shift` 차이도
같은 척도로 4.06~6.54/255 로, 시드 변동보다 작습니다.

한 장씩 눈으로 비교하면 계속 시드 운에 속습니다. 최소 3시드 세트로 보고, 가능하면
고주파 에너지·클리핑 비율처럼 **방향성 있는 지표**를 함께 확인하세요. 클리핑 같은
지표는 시드 노이즈에 묻히지 않고 일관되게 나타납니다.

## 튜닝 순서

1. 기본값으로 실행 → 콘솔 로그에서 격자·PiD 입력·창 수·패스 캔버스 확인.
   축 상한이 자동으로 걸리므로 색 회전은 신경 쓸 필요가 없습니다.
2. 너무 잘게 쪼개져서 느리면 → `context_pixel` 을 128 → 0. 축 상한 아래에서
   코어가 그만큼 커집니다(3840×2160 기준 24타일 → 12타일).
3. **패스 캔버스가 16.8MP 를 넘으면** `context_length` 를 낮추거나
   `tile_tolerance` 를 내립니다.
4. 이음새가 보이면 → `core_overlap` 64 → 128.
5. 디테일 부족 → `degrade_sigma` 0.06 → 0.10.
6. 선이 튀고 경계에 흰 테 → `model_shift` 2~8. 색 회전에는 효과가 없습니다.
7. 전역 톤이 밍숭맹숭 → BMK Wavelet Tone Restore 의 `levels` 조정.

## 트러블슈팅

- **하이라이트가 분홍/보라로 물듦, 하늘이 청록으로 뜸** — 타일 출력 축이 4096px 를
  넘은 경우입니다. v2.3 의 auto 모드에서는 구조적으로 일어나지 않습니다. 발생한다면
  ① `tile_shape=square` 에 `pid_input_size > 1024` 를 쓰고 있거나 ② `pid_input_size`
  자체를 1024 위로 올린 경우입니다(콘솔에 경고가 뜹니다). `context_length` 를
  낮추거나 `model_shift` 를 올리는 것으로는 해결되지 않습니다 — 축을 줄이세요.
- **타일이 예상보다 잘게 쪼개짐** — 먼저 `context_pixel` 을 확인하세요. 128 이면
  코어 상한이 `1024 − 256 = 768` 로 줄어 타일 수가 크게 늘어납니다(v2.3).
  다음으로 `context_windows` 가 꺼져 있는지 보세요. 창이 꺼지면 면적 예산이
  PiD 입력 기준(코어+컨텍스트)으로 바뀌어 훨씬 빡빡해집니다.
- **`타일 격자를 찾지 못했습니다` 에러** — `context_pixel` 이 `pid_input_size` 의
  절반 이상이면 어떤 격자도 축 상한을 통과하지 못합니다. `context_pixel` 을 줄이세요.
- **타일 하나조차 OOM** — `context_windows` 를 켜거나 `pid_input_size` 를 낮추세요.
  노드가 1회 자동 재시도합니다.
- **결과 색이 완전히 다름** — `latent_format` 과 인코딩 VAE 불일치. 콘솔 로그 확인.
- **`pid_vae` 에러** — `pixel_space` 이외를 고르면 로더가 즉시 막습니다.
- **짧은 면이 작은 이미지** — 1타일로 동작은 하지만 PiD 가 1024급을 기대하므로
  디테일이 부족할 수 있습니다. 앞단에서 미리 확대해 넣으세요.
- **배치 입력** — 항목마다 전체 캔버스를 만들어 마지막에 이어 붙입니다.
  초대형 입력에서는 batch 1 로.

## 설치

1. `bmk_pid_tiled_upscale.py` 를 `ComfyUI_BMK_Nodes/` 에 배치.
2. `__init__.py` 의 `_NODE_MODULES` 에 `"bmk_pid_tiled_upscale",` 추가
   (`bmk_load_image_crop` 과 `bmk_run_batch_grid` 사이, 알파벳 순).
3. ComfyUI 재시작 → `BMK/Image` 카테고리에서 두 노드 확인.

v2.1 → v2.2 도 로더에 `encode_vae` 가 맨 뒤에 추가된 것뿐이라 기존 배선이 유지됩니다.

**v1 → v2 는 위젯 구성이 바뀌었습니다.** 기존 워크플로우의 노드는 지우고 다시
추가하세요. v2 → v2.1 은 `tile_shape` 가 위젯 목록 맨 뒤에 추가되었을 뿐이라
기존 v2 배선은 그대로 유지됩니다(값은 기본 auto).

**v2.2 → v2.3 은 위젯이 추가·삭제되지 않아 배선과 저장된 값이 그대로 유지됩니다.**
다만 동작은 두 군데 달라집니다.

- **같은 설정에서 타일 수가 늘어날 수 있습니다**(축 상한). 축이 이미 상한 안이던
  조합은 그대로입니다. 결과물의 색이 개선되는 대신 처리 시간이 늘어납니다.
- **`color_match` 기본값이 `mean` → `mean_std` 로 바뀌었습니다.** 이미 워크플로우에
  저장된 값은 그대로 유지되므로, 기존 워크플로우에서 `mean` 으로 두었다면 실질적으로
  보정이 꺼진 상태입니다(위 실측 참고). `mean_std` 로 바꾸는 것을 권합니다.

## 한계

- PiD 는 네이티브 4배 고정이라 배율을 고를 수 없습니다. 순 2배가 목표여도 4배 연산
  비용을 지불하고 사후 축소해야 합니다.
- 타일 간 전역 일관성(화면을 가로지르는 넓은 그라데이션)은 타일 방식의 구조적
  약점입니다. `color_match=mean_std` 가 대부분 상쇄하지만 완전한 복원은 Wavelet
  Tone Restore 의 저주파 이식에 의존합니다.
- 축 상한 때문에 큰 소스일수록 타일 수가 빠르게 늘어납니다(8192² 기준 81~144장).
  PiD 가 1024 입력으로만 학습된 데서 오는 근본적 제약이라 우회로가 없습니다.
- **`model_shift` 는 두 소스 실측으로 성격이 정리됐습니다**(위 절 참고). 최종 출력
  기준으로는 기본값 0.0 에서 바꿀 이유가 없고, 노드 출력을 그대로 쓰는 경우에만
  3.0 이 유의미합니다.
- 노드 출력의 크로마 오차는 후단 BMK Wavelet Tone Restore 가 약 75% 를 걷어내는
  데 의존하고 있습니다. 이 노드를 빼면 색이 눈에 띄게 나빠지므로 배선을 유지하세요.
